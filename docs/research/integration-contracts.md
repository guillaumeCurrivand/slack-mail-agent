# Slack and Gmail integration contracts

Verified against primary documentation on 2026-09-17. Implementation recommendations below are explicitly identified; they are not additional product decisions.

## Slack ingress and replies

- Verify `X-Slack-Signature` against `v0=` plus the hex HMAC-SHA256 of `v0:{timestamp}:{raw request body}` using the signing secret. Preserve raw bytes before JSON or form decoding; use constant-time comparison and reject timestamps differing from server time by more than five minutes. Header names are case-insensitive. [Slack request verification](https://docs.slack.dev/authentication/verifying-requests-from-slack/)
- Subscribe to `message.im` with bot scope `im:history`; enable the App Home Messages tab and add `chat:write` for replies. Direct-message events have `channel_type: "im"`. [DM event](https://docs.slack.dev/reference/events/message.im/), [App Home](https://docs.slack.dev/surfaces/app-home/)
- Events require a successful response within three seconds; Slack retries failed delivery. The event wrapper has an `event_id`. The URL-verification flow returns the supplied challenge. **Recommendation:** verify first, persist an event/job atomically keyed by event ID, then acknowledge; ignore bot-authored events and non-DM events. Resolve the user from signed `team_id` and event `user`, never from a model-generated identifier. [Events API](https://docs.slack.dev/apis/events-api/)
- Interaction requests are form encoded with a JSON `payload` field and also need a 200 acknowledgment within three seconds. Use a job for mailbox work. `response_url` expires for practical response use after 30 minutes and supports up to five responses, so use Web API for durable asynchronous replies. [Handling interaction](https://docs.slack.dev/interactivity/handling-user-interaction/)
- A `block_actions` payload identifies `team.id`, `user.id`, channel/container, and `actions[].action_id`/`value`. **Recommendation:** put only an opaque run/action reference in a button; load its immutable preview from storage, check team/user/channel ownership and expiry, and consume confirmation transactionally once. An action ID alone is not authorization. [Block action payload](https://docs.slack.dev/reference/interaction-payloads/block_actions-payload/)
- `chat.postMessage` accepts a JSON payload containing the existing DM channel ID, text fallback, and optional blocks. Check both HTTP status and Slack's JSON `ok` flag. Disable link/media unfurling for email-derived content and avoid generating mentions from untrusted email text. Rate limiting is generally one message per second per channel; respect retry instructions. [Posting messages](https://docs.slack.dev/reference/methods/chat.postMessage/)

## Per-user Google authorization

- Use a Web application OAuth client with an exactly registered redirect URI, authorization-code flow, and `access_type=offline`. Exchange codes on the server. Refresh tokens are not returned on every authorization; retain an existing refresh token if the token response omits it. `prompt=consent` can request consent again when necessary. Check granted scopes before enabling mailbox operations. [Google web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server)
- Request `openid email https://www.googleapis.com/auth/gmail.modify`. `gmail.modify` is a restricted scope and permits reading mail and modifying it except immediate permanent deletion; do not request full `https://mail.google.com/`. **Recommendation:** the adapter exposes no send or permanent-delete method even though modify is a broad scope. [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)
- Generate a random OAuth `state` bound to the browser session and originating Slack identity; compare it on callback. Include a distinct random OIDC nonce and verify its returned claim. The `sub` claim is the stable Google account identifier; email may change. [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)
- Validate the ID-token signature, audience, issuer, and expiry with Google's library. Require `email_verified` and an allowed Workspace `hd` claim. Checking only an email suffix is insufficient. The authorization request's `hd` is a login hint, not the enforcement boundary. [ID-token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)
- Google's Node library supports `generateCodeVerifierAsync()`, an S256 code challenge in `generateAuthUrl`, and `codeVerifier` in `getToken`. **Recommendation:** use PKCE as additional protection, storing the verifier server-side with the short-lived state. [Google OAuth client source](https://github.com/googleapis/google-auth-library-nodejs/blob/main/src/auth/oauth2client.ts)
- **Application binding recommendation:** a signed Slack DM requests a one-use, expiring connect link. Opening it creates a browser-bound OAuth session. Store team/user ownership server-side, not in caller-supplied callback parameters. Finish by asking the originating Slack user to confirm the linked address before activating/replacing credentials. This prevents a forwarded link alone from changing that user's active mailbox. Encrypt refresh tokens at rest; enforce one active account per Slack user and avoid linking one Google subject to multiple Slack identities.
- Internal-only OAuth configuration is available when the Cloud project belongs to the Workspace organization. Workspace administrators can still block applications. Setup must enable Gmail API, configure Internal audience and the OAuth client, and ensure the organization permits the required scopes. [Restricted-scope exceptions](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification), [OAuth app states](https://developers.google.com/identity/protocols/oauth2/production-readiness/overview)

## Selecting and changing individual messages

- `GET /gmail/v1/users/me/messages?labelIds=INBOX&maxResults=100` selects inbox messages. The official guide explicitly states newest-first ordering. The response contains IDs/thread IDs only; retrieve each message separately. Freeze this selected ID set for a preview rather than relisting after approval. [List guide](https://developers.google.com/workspace/gmail/api/guides/list-messages), [List reference](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list)
- A message's `internalDate` determines inbox ordering; it is preferable to the sender-controlled Date header. A message includes `labelIds`, last-modification `historyId`, and recursive MIME `payload`. `filename` identifies attachment parts. **Recommendation:** read body text from nonattachment MIME parts only, prefer text/plain, sanitize HTML to text as fallback, and never fetch remote links or attachments. Treat truncated or unavailable bodies as uncertain. [Message resource](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages)
- Apply labels with `POST /gmail/v1/users/me/messages/{id}/modify`, JSON `{addLabelIds: [...], removeLabelIds: [...]}`; success returns a Message. It accepts up to 100 labels in each add/remove list. Archiving removes the system `INBOX` label. Use message methods, not thread methods. [Modify](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/modify), [Label semantics](https://developers.google.com/workspace/gmail/api/guides/labels)
- Trash with `POST /gmail/v1/users/me/messages/{id}/trash`; reverse with `/untrash`. Both take an empty request body and return a Message. Neither is permanent deletion. Record/reconcile label state when restoring; do not assume untrash alone reconstructs the exact original inbox state. [Trash](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/trash), [Untrash](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/untrash)
- Create approved missing labels via `POST /gmail/v1/users/me/labels` with a Label object including `name`; success returns the created Label and ID. Reuse a matching existing label and recover duplicate creation races by relisting. [Create label](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.labels/create)

## Confirmation, concurrent changes, and undo

**Implementation recommendations based on the API contracts:**

- Persist original labels/history ID and the exact approved delta per message. Serialize agent mutation runs per account. Before execution, reread message state and skip/repreview changed items rather than silently applying an outdated plan.
- The modify contract has no documented conditional history-ID argument or compare-and-swap primitive. Rechecking narrows the race with external Gmail clients but does not eliminate it. Report this limitation honestly; never call it a transaction across Gmail messages.
- Journal each individual mutation before/after dispatch. On timeout, reconcile current state before retrying. A partially completed run reports successes, failures, and uncertain outcomes separately. Do not retry an entire run blindly.
- Undo only this run's changes: remove labels the run added, restore labels it removed, and untrash messages it trashed. Preserve unrelated labels added later. If relevant state changed afterward or an outcome is ambiguous, skip the item and explain; do not overwrite the user's intervening work.
- `historyId` is a change cursor, not a lock. History records are chronological, IDs have gaps, and expired/invalid starting IDs typically return 404. Retention may be only hours, so a 30-day action log does not imply 30 days of retrievable Gmail history. A 404 requires fresh synchronization; use current-state checks and conservative undo when history is unavailable. [History API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list)

No real Slack messages or mailbox operations were performed for this research.
