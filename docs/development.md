## Approved behavior

Each Development project connects exactly one Slack channel, 1–100 ClickUp Folders (all non-archived Lists), 1–20 distinct repositories and one common Cursor skill. Every configured Folder offers every repository in the project; a ticket may target one or several repositories. Folder and repository collections are configured in the Slack form without reorganizing ClickUp. Everyone in the channel may interact with it. On 12/10/2026 the User clarified that Development must work in both project Slack channels and private DMs. Configuration, repository selection, status and workflow controls are available in both, with fresh project-channel membership checks. Bot membership is required. Existing personal ClickUp OAuth connections and other Modules' state remain private.

Multiple projects may share the **same channel, ClickUp Folder and List** while using different repositories. The User approved choosing one or several repositories for a ticket on 12/10/2026. Shared-folder tickets require a repository selection, manually confirmed by default or produced by the opt-in automatic mode below; folder membership alone never authorizes every repository.

A ticket link posted in the connected channel queues an investigation once its repository selection is known (known directly for a single destination, or detected in automatic mode for several). The local worker reads the ticket snapshot, comments and repository using the configured skill, then responds in the original Slack thread with an actionable result or specific missing-information questions. Human thread replies before authorization are saved as attributed ClickUp clarification comments and trigger reassessment. Bot messages, edits, unrelated channels and unsigned events are ignored. Standard `https://app.clickup.com/t/<task-id>` links are supported; custom-ID URLs should be replaced with the task's standard link. Arbitrary linked pages are not fetched by the server.

An enabled Folder is polled once per minute. A human selecting `Ready for AI` authorizes implementation, including for subtasks independently carrying that status and tickets never linked in Slack. Already-ready tickets are eligible when the project is first enabled. The first accepted snapshot freezes requirements; the worker does not reread them during implementation. Moving away from Ready for AI must be observed by a poll before moving back can authorize another run. `development retry <run-id>` explicitly retries a blocked or cancelled run against its frozen snapshot. The same command can explicitly retry a `reporting_error` build whose commit was already pushed: it reads the current ticket and queues a new build, which the worker publishes to its currently configured branch. The previous commit stays on the branch named in that result. Ready for AI still does not start that new build by itself. A repeated delivery or repeated poll never authorizes another attempt.

Implementation runs sequentially per repository with two attempts total (initial plus one retry), no execution deadline, and a separate checkout for each run. The controller runs the configured automated checks; changes to visible behavior require configured browser checks. Missing information or failed necessary verification blocks publication, posts the blocker to Slack/ClickUp, and leaves unfinished work in its private checkout. Other independent queued work may proceed.

After successful verification, the controller creates one descriptive English commit per ticket and selected repository and pushes it to the locally configured destination branch, never force-pushing. `branch` defaults to `maintenance`. On 11/10/2026 the User approved any destination whose name uses the same grammar as `baseBranch`; the EOA pilot uses `stage/maintenance-ia`. The coding agent supplies a separate English `commitTitle`; the controller adds `fix(clickup:<task-id>):` instead of copying a possibly French ticket title. Missing or multiline titles block publication. ClickUp/Slack reports and clarification questions remain French. It changes the ticket to **`to build`** only after confirmed pushes from all selected corrections; each repository reports its own commit link, summary and test results. Multiple tickets may accumulate on the configured maintenance branch. Humans review, open the PR/MR, merge to the configured base branch (`preprod` for EOA), deploy and close tickets. If the base branch and that maintenance branch diverge, a human reconciles them; the worker does not create surprise merge commits. After maintenance is merged normally into the base branch, the next run starts from its newer tip.

In the default manual mode, posting a ticket link registers it without starting paid analysis when its Folder has several configured repository destinations, including suspended projects. Choices and confirmations are owner/channel/message-bound and expire after 24 hours. The first confirmed choice wins across users; stale choices cannot overwrite it. Slack membership, ClickUp ticket ownership and current project configuration are rechecked. A pending choice starts no work. Confirming starts one analysis per selected repository for a non-ready ticket; if it is already Ready for AI, the next poll admits one correction per selected repository. The confirmed selection is shared with channel members and retained for later Ready for AI cycles. Users can explicitly revise it through the guided actions below; concurrent changes are checked against a saved selection revision, so a stale confirmation cannot overwrite a newer choice.

All corrections for an authorization are inserted atomically with the same frozen ticket snapshot. A missing, changed or suspended selected project holds admission of the entire new batch. Existing queued work only starts in enabled projects whose repository/channel/Folder/skill still match its snapshot; already-started work can finish. Adding another project never silently redirects work. Historical unassigned queued work is held when a Folder becomes shared; existing runs cannot be adopted into a new repository selection automatically. Reconcile old claims/results with the operator before selecting repositories for an already-processed ticket. New tickets can be selected normally.

Each repository has its own checks, commit, branch and report, labeled with the project and repository name. Project history includes the repository on each run. The shared ticket moves to **to build only after every selected correction has a confirmed push**. A successful frontend waits if the backend is blocked; there is no cross-repository rollback or automatic merge/deployment. Use **Relancer…** on the blocked repository's treatment to retry only that correction; a successful sibling is retained. Superseded retries cannot start another run. Uncertain status delivery retains the shared effect checkpoint and does not authorize another build. Thread clarifications are added to ClickUp once, then analyzed in each selected repository while requirements remain open.

The ticket list remains available if a routing notice's delivery is uncertain; notices are not blindly replayed and do not block discovery of other tickets. Unrelated Folder mismatches do not produce one error per project in a shared channel. Automatic repository inference requires the explicit project setting described below. Independent repository tests do not prove frontend/backend integration compatibility; configure the required services and cross-component checks on the worker. Existing project configurations are not automatically opted in.

For an unassigned ticket posted in the project channel or discovered in Ready for AI, the local worker inspects each candidate repository's actual source and interfaces in a separate read-only `scope` run. It receives the same ticket snapshot and candidate names/URLs, and reports whether its repository requires changes, does not require changes, or remains uncertain, with evidence or questions. Detection does not run setup, services, browser previews, checks, commit or push. The usual local journal and two-attempt limit apply. This is a trusted local worker, not a security sandbox. Cursor billing remains separate and scales with the number of candidate repositories; passive navigation never starts detection.

All projects offering destinations in the Folder must be active, use the same Slack channel and opt into automatic mode. Otherwise the manual picker remains available. A worker must advertise detection support and the exact configured repository/skill before claiming an inspection. Older workers cannot claim these runs; missing worker entries leave inspection pending, visible in ticket history. The server waits for every candidate's conclusive result and selects **all** included destinations. It posts the explanation in the project channel and saves it under **Tickets et dépôts**. Non-ready tickets then receive normal analyses in selected repositories; Ready tickets receive the existing atomic correction batch on the next poll. Ready for AI remains necessary for implementation, and `to build` still waits for every selected correction's confirmed push.

Detection runs once per unassigned ticket. Repeated links, polls and result deliveries do not repeat paid inspections. Any uncertain/failed/cancelled result, no relevant destination, or a change to requirements or candidate configuration leaves selection to a human; pending unclaimed inspections are cancelled. Ticket status alone may change while inspection runs; current Ready for AI controls build admission. The operator must reconcile legacy review/build runs before automatic or initial manual assignment. Scope runs are excluded from that legacy restriction because they cannot publish.

Use **Choisir les dépôts** to override pending or inconclusive detection through the existing personal confirmation. It cancels unclaimed inspections and invalidates late results; already-running inspections can finish without changing the choice. Detection runs cannot be retried through build/review retry controls: choose the repositories manually after resolving the reported questions. Saved manual or automatic selections are retained for subsequent Ready cycles; changing mode does not reroute existing assignments. Existing selection-edit eligibility still applies after a selection or correction exists. No cross-repository rollback, merge or deployment is added. See the [updated routing decision](adr/0010-shared-ticket-repositories.md).

## Guided state actions

The User approved guided repository changes, queued cancellation and eligible retries on 13/10/2026. These controls work in both project channels and private DMs, with the same membership and owner/conversation/message binding as other Development actions. The clickable **État / actions** column in **Tickets et dépôts** opens assignment controls. The clickable **État** column in **Traitements — project name** opens the run and its available actions. Buttons below each table provide a fallback for clients without interactive table cells. These controls do not edit ClickUp status or let users declare a run running/completed manually.

**Modifier les dépôts** starts a prefilled draft. Review and separately confirm the new selection. The mutation preserves historical runs and retained repositories’ analyses, cancels only removed repositories’ unclaimed queued analyses, and starts analysis only for newly selected destinations when the ticket is not Ready for AI. An identical selection is a no-op. If the ticket is already Ready for AI, confirming a changed selection explicitly authorizes the next complete correction batch for the new selection. Selecting nothing is not permitted.

Repository changes are refused while any ticket run is running, publishing or awaiting publication reconciliation, whenever a commit exists, or whenever a correction exists in a state other than cancelled. Cancel all queued corrections first; started or completed corrections require operator reconciliation. Completed/blocked analyses without commits do not prevent a change. Pre-routing historical runs still require reconciliation before initial assignment. Project locks serialize the confirmation with worker claims and polling; a saved revision rejects stale concurrent selections. Old drafts from before an existing selection cannot become edit authorizations.

**Annuler ce traitement… → Confirmer l’annulation du traitement** cancels only that queued, unclaimed run, including in a suspended project. It retains the run as **Annulé**, its frozen snapshot and batch mapping; other repositories and external ClickUp/Slack results remain intact. Confirmation fails if a worker claimed it meanwhile. Cancelling a correction consumes the existing Ready authorization: an unchanged Ready for AI status does not recreate it at the next poll. A later observed non-ready → Ready transition, an eligible explicit retry, or a separately confirmed changed repository selection can authorize new work. Cancelling an analysis does not cancel a separately authorized correction or prohibit a later explicit ticket link/clarification.

**Relancer…** also accepts cancelled runs, with the frozen requirements and existing two-attempt-per-run policy. The project must be enabled, the destination must still belong to the ticket’s current selection, and no equivalent run may already be active. Retry replaces that batch member without replaying successful siblings. A cancelled correction prevents the batch from reaching `to build` until its replacement succeeds. Repeated confirmations never repeat cancellation, assignment or retry. Uncertain external publication still follows the [operator recovery procedure](#recovery-access-and-retention); these actions do not erase effect checkpoints or mark an unverified commit delivered.

## Local worker setup

Use Node 24+, Git, an authenticated Cursor CLI, repository access and the project's development prerequisites. A long-running app can inherit an older PATH than a newly opened PowerShell session. Check the installed launcher before concluding the CLI is absent. Follow the official [Cursor installation](https://cursor.com/docs/cli/installation), [authentication](https://cursor.com/docs/cli/reference/authentication) and [headless](https://cursor.com/docs/cli/headless) documentation for the actual workstation.

Copy [development-worker.example.json](../development-worker.example.json) to `development-worker.local.json` and edit it. `repository`, `id` and `skill` must match a repository in the server’s project. Multiple local entries may share `id` when their repository URLs differ; duplicate project/repository pairs are rejected. The worker advertises these exact destinations when claiming work, so a worker configured for a subset cannot consume another repository’s run. Older workers remain usable for single-repository projects only; update the server before restarting an updated worker. Use a dedicated `stateDirectory` outside an existing working checkout; the worker creates separate clones beneath it. `skillPath` points to a worker-compatible `SKILL.md`; the [maintenance skill template](../skills/development-maintenance/SKILL.md) provides investigation, verification, French reports and English commit titles. Unlike an interactive ticket skill, it leaves commits, ClickUp writes and publication to the controller. Include project-owned supporting skill files in the repository or make referenced paths available on the worker.

For Orientaction on the existing Windows workstation, follow the [EOA runbook](development-eoa.md) instead of using the generic commands unchanged. It includes explicit project Node selection, the npm peer-dependency option, frontend environment preparation, backend startup, ngrok tunnel and matching browser allowlists. Keep project subprocess runtimes separate from Mayassistant's Node 24+ runtime.

`agent` is an executable-and-arguments array. It defaults to `["agent"]`; use the installed CLI's executable or interpreter entry point. Child processes do not use implicit shell expansion. On Windows, `.cmd`/`.bat` launchers cannot be passed as native executables: configure a supported executable/interpreter launcher, or run the worker and Cursor in WSL. Do not interpolate ticket contents into shell commands.

Keep worker/tool and project runtimes separate. The worker requires Node 24+ and fails before configuration/lock acquisition on an older runtime. For the Windows EOA profile, use [start-development-worker.ps1](../scripts/start-development-worker.ps1), whose default is the installed Node 25.8.1 executable; `-NodePath` supports another installation, and `-Check` validates it without starting work. Pin browser MCP to a physical compatible executable too. Project commands may select an older runtime through a child-process PATH or explicit executable. The agent prompt prohibits global NVM/PATH changes; this is a trusted-agent instruction, not an OS sandbox. See the [runtime separation procedure](development-eoa.md#keep-the-worker-and-project-node-versions-separate).

For Cursor's Windows PowerShell launcher, use `["powershell.exe", "-NoProfile", "-File", "C:/Users/YOUR_USER/AppData/Local/cursor-agent/agent.ps1", "--trust"]`, replacing the path with the installed launcher. `--trust` acknowledges the per-run workspace in headless mode. This avoids relying on PowerShell command discovery from a native Node child process. An explicit launcher was verified with `--version` on 04/10/2026; that does not verify account authentication or a coding run.

`setup`, `checks` and `browserChecks` are trusted local command arrays. Adapt the example to the project. `setup` prepares each new checkout without modifying non-ignored files. `checks` must contain at least one real validation command. Configure either `browser` for MCP exploration plus independent scenario replay, or `browserChecks` for trusted command-based browser checks. Worker success depends on their exit codes; Cursor's textual claims alone do not count as passing checks. No live browser suite was exercised during implementation.

Optional `services` are trusted local dependencies started in array order after checkout preparation and before the frontend preview or any Cursor attempt, for both review and implementation. Each entry has a unique `id` (except reserved `preview`), `cwd`, executable/argument array `start`, loopback HTTP `readyUrl`, optional `startupTimeoutMs` (same bounds/default as the preview), and optional `reuseExisting` (false by default). The worker waits for HTTP success before starting the next service. An optional `ngrok: {publicOrigin, upstreamPort}` requires the local ngrok API to report an HTTPS tunnel matching that exact origin and a loopback HTTP upstream on the expected port. It never silently accepts a different tunnel hostname. All services use the same filtered subprocess environment as the coding worker.

An occupied service port is rejected unless `reuseExisting:true` and the readiness check passes. This is an operator-approved reuse of that endpoint, not proof of process identity. Existing services are never terminated. On normal completion or failure, the worker stops its frontend and newly started dependencies in reverse order; partial startup failure also cleans up earlier processes. Logs are `preview.log` and `<service-id>.log` in the run directory. Environment startup failure blocks the run before consuming a Cursor attempt. Hard process/machine termination still requires inspecting remaining processes before recovery; the worker does not claim crash-proof teardown. EOA's backend → ngrok → frontend profile is in the [runbook](development-eoa.md#worker-configuration).

Cursor's JSON output envelope may contain progress prose before the final report. The worker accepts one complete final JSON object, optionally fenced, and validates its full report schema. Multiple objects, trailing prose, malformed reports and failed CLI envelopes are rejected. A valid `actionable:false` report returns the French clarification without spending a second attempt; parsing it does not authorize implementation or bypass controller checks.

Cursor's [integrated browser](https://cursor.com/docs/agent/tools/browser) is documented in the editor; this worker uses [CLI MCP support](https://cursor.com/docs/cli/mcp) with [Microsoft Playwright MCP](https://github.com/microsoft/playwright-mcp). ### Browser MCP and replay configuration

In a local project entry, configure:

```json
{
  "branch": "maintenance/ai",
  "baseBranch": "preprod",
  "browser": {
    "url": "http://127.0.0.1:3199",
    "start": ["powershell.exe", "-NoProfile", "-Command", "$env:PORT='3199'; $env:HOST='127.0.0.1'; $env:BROWSER='none'; npm start"],
    "allowedOrigins": ["https://YOUR_APPROVED_TEST_API"],
    "accountsFile": "C:/YOUR_PROJECT/browser-accounts.json",
    "accounts": ["beneficiary", "admin", "beneficiary_2"]
  }
}
```

Replace the test API and account path with approved local values. Omit account fields when login is unnecessary. Flat account files contain objects keyed by role, each containing `email` and `password`. For grouped files such as `{ "local": { "admin": { ... } }, "live": { ... } }`, set `browser.accountsGroup` to the explicitly selected group; EOA uses `"local"`. Both Cursor's instructions and the independent replay use that group exclusively, with no fallback to another group. Omitting `accountsGroup` preserves flat-file behavior. Only roles explicitly allowed by the operator may be selected. Credentials stay in that local file; scenario login steps reference the role and field, never a literal password. The MCP exploration session is isolated from the replay browser. Do not copy production credentials into either session. Missing files/groups/fields produce a specific sanitized failure reason in Slack and `browser-result.json`, with the step/action but no credential value.

The controller rejects an occupied preview port, starts the configured command in its own per-run checkout, and stops that process tree after the run. `browser.startupTimeoutMs` sets the readiness deadline in milliseconds: default 240000 (four minutes), allowed range 1000–1800000; EOA uses 600000 (ten minutes) for cold compilation. The deadline includes HTTP probes and retry waits. A process crash fails promptly; a timeout stops the preview and identifies the setting in its error. Coding itself still has no execution deadline. Project dependencies and required development environment must work in a fresh clone. A missing environment blocks the run.

For a visible change, Cursor uses MCP to explore the preview and returns a `browserScenario` containing navigation, interaction and assertions. The controller validates and independently executes those steps with Playwright in a fresh browser. It saves `browser-<attempt>/browser.png` and `browser-result.json` outside the checkout. Failed/missing scenarios block publication. This proves the supplied scenario passed, not that the agent chose exhaustive coverage. The replay restricts network requests to the preview plus `allowedOrigins`; MCP restrictions are configuration controls, not a sandbox. Keep both allowlists consistent.

Supported steps are `navigate`, `click`, `fill`, `fillAccount`, `press`, `expectVisible`, `expectHidden`, `expectText` and `expectURL`. The exact parameter shapes are supplied in the controller prompt. More complex flows not expressible by these steps require an explicitly configured command-based browser check. An empty `browserChecks` is valid when `browser` is configured; without either, visible changes cannot publish.

After `fillAccount`, a scenario must wait for an assertion before an explicit subsequent `navigate`. In particular, clicking Login does not wait for asynchronous authentication: use `expectURL`, `expectHidden` on the login form, or an authenticated-page assertion before navigating to the feature. The replay rejects a missing wait with a specific French reason instead of interrupting login and failing at an unrelated later selector.

## Recovery, access and retention

`development status <project>` shows recent queued/running/completed/blocked operations and folder-read failures. Project settings, selections and runs remain shared domain data. Controls and confirmation messages stay in the DM or channel thread where they were opened. Ticket links and clarification replies continue in the project channel; worker reports and ClickUp comments retain those shared destinations, even when a repository selection or retry was confirmed privately. The worker token grants trusted access to Development snapshots and results for the configured Slack workspace. It does not grant access to other Modules' tables.

Running claims do not expire, because there is no execution time limit. `worker.json` stores a stable worker identity; `worker.lock` prevents overlapping local instances. After a hard crash, first establish that the old worker and its Cursor child processes have stopped, then remove only the stale lock file and restart using the same state directory. Do not create a new worker identity to bypass an active claim. An interrupted/uncertain Cursor call is reported as blocked instead of dispatched twice. Local journals retain prompts, outputs, checks and separate checkouts for inspection.

An already-pushed commit is recovered by SHA. Lost push responses are checked against remote ancestry; no new commit is created. If publication cannot be confirmed, the saved SHA is reported and a status toggle cannot start another build for that ticket. An explicit `development retry` of that `reporting_error` run can. It does not rewrite or republish the saved commit; the worker checks out its current configured branch for the new run. Replaying the uncertain ClickUp/Slack delivery remains a separate operator recovery.

External ClickUp/Slack writes receive a durable sending marker first. Unknown outcomes become `reporting_error` and are never blindly replayed; inspect the actual ticket/thread and reconcile that exact effect before recovery. The current pilot requires operator database recovery for uncertain deliveries: inspect `development_runs` and its `development_effects` rows, verify whether each external effect happened, mark verified effects `done` (record the Slack timestamp in `detail` for a verified Slack post) or delete only verified-not-delivered effect rows, then set the run back to `reporting`. Restore its `development:finish:<run-id>` integration job to `queued`, clear `finished_at`, set `available_at=now()`, and restore its payload to `{"type":"finish","run":"<run-id>"}` because completed jobs clear their payload. If queue retention already removed that job, enqueue a new Development integration job with the same payload and configured workspace identity. Stop conflicting work and take a backup first. Never mark an unverified effect done, delete the run, rerun coding for a pushed commit, or clear all delivery markers. An operator UI for this exceptional recovery is future work.

For the pilot, Module configuration, minimal deduplication state, snapshots and effect history are retained until the operator deliberately decommissions the project; local worker evidence is also retained. Protect and back up this data. Do not delete an active run's journal, worker identity or effect checkpoints. A time-based retention policy is deferred until recovery requirements are validated. Disabling the Module preserves state and exposes no worker routes. Other Modules' retention contracts remain unchanged.
