# Atomic work admission and module-scoped worker locks

The two existing on-demand operations, Mail Sorter's sort and Slack Unanswered's search, need to reject overlapping starts for the same User while keeping DM navigation and the other Module responsive. A Slack delivery ID cannot provide this guarantee: separate clicks have separate IDs, and their response jobs may run after the first operation finishes. The previous advisory lock covered every job for one User, including slow provider calls, so even menus waited behind a scan.

The shared ingress now records an operation slot keyed by owner, Module and operation in the same SQL statement that inserts the original job or a duplicate-status job. PostgreSQL's unique key and row lock serialize competing admissions. The slot holds the original job ID while active. A duplicate gets a durable, separate core response job that names the original. Worker completion or terminal failure changes job status and releases its slot in one SQL statement. Queued and retrying work retains the slot; a completed Preview does not. Exact typed commands use the same admission path as menu buttons. Mail requests whose intent needs later AI interpretation capture the active sort ID at receipt, then claim the slot atomically if they resolve to a sort. Menu starts are admitted only after validating the recorded owner, DM and Agent-message identity, then the Module validates the control again at execution.

The worker uses an advisory lock per owner and Module, and chooses the oldest ready job for that pair. This preserves ordering and serialization for mail state and mutations, while core navigation and Slack Unanswered can run on separate worker lanes. Mail retention cleanup takes the same mail lock. At least two worker lanes are required for responsiveness. Spending remains one shared transactional budget ledger with per-user limits and module attribution; no separate allowance is created by scheduling work concurrently.

This is bounded to the two existing work operations. Existing mail scan, approval, mutation and recovery checkpoints and Slack AI attempt checkpoints remain in their Modules. A crash before terminal completion leaves a retryable job and active slot; a crash after the atomic terminal update leaves a released slot. Disabled-module jobs remain paused with their slots active until the Module is re-enabled and reaches a terminal state.

The former whole-owner lock gave ordering between unrelated Modules, including their read-only work. The Modules do not share mutable domain state; core budget reservations already serialize in the database. This narrower lock therefore preserves the required conflicting mutation order within a Module while allowing independent work to proceed. See the [product specification](../product-spec.md) and [module guide](../adding-a-module.md) for the current contract.

ClickUp's OAuth HTTP callbacks use brief database transactions taking the same owner/Module advisory lock as the worker. External OAuth/API calls occur between these transactions; holding the lock across those calls would delay disconnect. A persistent authorization generation changes on activation/disconnect and is checked after provider calls, preventing a cancelled callback from storing credentials even when the active account has returned to its previous disconnected state. Pending credentials and their Slack confirmation job commit together, preventing an orphan proposal when queue insertion fails. Credential-free generation records persist as invalidation metadata after disconnect. Current ClickUp behavior is defined in the [feature contract](../clickup.md).
