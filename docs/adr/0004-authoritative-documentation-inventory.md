# Authoritative shared inventory in Documentation

During the design interview, the user selected the database as the authoritative company inventory after importing the existing spreadsheet. Independently editing both Google Sheets and the database would require synchronization and conflict rules; one authority keeps shared edits and their history consistent. Documentation will expose this shared inventory through private Agent interactions, with inventory facts and documentation links as its initial knowledge scope.

The user chose to apply confirmed field changes even when another person edits the record after the preview, favoring simple collaborative editing over rejecting stale confirmations. An implementation must serialize commits, preserve unrelated fields, and record the actual before/after values atomically with each mutation. Record versions may support history but must not become a reason to reject these confirmations.

Confirmations expire after 24 hours; archived targets require explicit restoration before editing. These conditions do not introduce rejection because of intervening field edits. Changes affect individual records; bulk mutations and controls restoring earlier field values are deferred.

Use the existing PostgreSQL with workspace-owned inventory/history and actor-owned interaction state. Existing worker locks serialize only one User's work within a Module; transactional record coordination must serialize shared inventory commits across Users. This extends the ownership assumptions of the [module guide](../adding-a-module.md) and [worker locking decision](0003-operation-admission-and-module-locks.md), while preserving the private ownership of existing Modules.

The User approved the ten-ticket breakdown and authorized implementation of tickets 01–10. The target contract and delivered-slice status live in [Documentation](../documentation.md), linked from the [product specification](../product-spec.md). The existing spreadsheet remains authoritative until a separately reviewed import is applied and verified; local structured inventory mutations do not perform that transition. Spreadsheet exports, bulk mutations, history-value restoration controls, document-content ingestion, and vector retrieval are deferred.

Ticket 01 creation commits its Project, initial history and applied confirmation checkpoint in one PostgreSQL statement. A conditional update locks the actor/DM-bound confirmation row, so separate delivery IDs and simultaneous confirmations cannot repeat the effect. Its stable target identifier is reserved when the proposal is saved. This gives creation its needed coordination without changing the shared runtime or serializing all workspace navigation. Lifetime inventory/history are separate from ephemeral actor state, and cleanup retains checkpoints needed by pending work.

Ticket 02 editing uses one PostgreSQL statement with materialized row-locking reads: lock the eligible confirmation first, then its workspace-shared Project with `FOR UPDATE`. The second read waits for another actor's transaction and uses the resulting current values. Merge only saved replacement keys into that locked record; derive history from the actual changed keys and atomically save the edit, history and terminal outcome. A satisfied selection records its terminal outcome without fabricating a change entry. A missing target records failure without an edit. These persisted outcomes prevent later retries from overwriting an intervening change. This coordination is Module-owned and does not alter worker locks or introduce optimistic-version rejection.

Ticket 03 preserves the existing Project tables and old controls while adding a shared typed table for Technologies/Components and its foreign-key-backed history. Confirmations gain a record kind, defaulting old rows to Project. Keeping a separate record-history table preserves database referential integrity for both stores without dropping the existing Project history foreign key; shared History unions their entries. Technology/Component mutations share one implementation of record locking, selected-field overwrite, actual history and effect checkpointing.

Components have a fixed Project parent backed by a workspace-composite foreign key. Technology relationships are bounded arrays of stable identifiers in the Component's fixed fields, rather than copied catalog values. Module-owned validation checks referenced identifiers/kinds/workspace before saving a proposal and at commit; commit locks referenced rows with `FOR KEY SHARE`. This fits the current single-record mutation contract and allows catalog renames without updating Components. There is no user deletion path; future lifecycle/import work must preserve relationships and use the same validation boundary. Missing catalog records always require a separate confirmed creation.

Ticket 04 extends the typed records/history store for Hosts/services and Hosting entries, preserving existing confirmation defaults and Project/Component controls. Hosting entries have fixed Component parents through a workspace-composite self foreign key; service references use stable identifiers in their fixed fields. Proposal validation checks reference kinds and workspace, and apply locks the current Component and Host/service with `FOR KEY SHARE` before atomically saving. Service costs remain shared catalog values rather than copied Project expenses. Partial Host/service replacements are checked against the commit-time merged record so an intervening edit cannot leave a known cost without currency. This is value validation, not stale-version rejection. Migration extends the existing kind/parent constraints and adds the Component reference; it does not move or erase existing records/history.

Ticket 05 reuses the typed records/history store for Tools. Bounded arrays of stable Project identifiers follow the existing Technology relationship pattern and fit the single-record confirmation contract without copying Project names or inferring links from usage text. Proposal validation resolves exact names/aliases; apply validates the merged record and locks the referenced workspace Projects with `FOR KEY SHARE` in identifier order. This preserves links through renames and commits record/history/outcome together. Future lifecycle/import work must preserve this reference-validation boundary. Company-wide status is independent of the Project array, so both forms of usage can coexist without manufacturing relationships. Referents remain descriptive fields under the existing workspace access boundary.

Ticket 06 keeps archival state in a non-editable boolean column on each existing inventory table, preserving all stable identifiers, foreign keys and business fields. Archive and Restore use the same confirmation-then-target lock order as edits, and atomically append actual lifecycle history with the terminal confirmation outcome. Terminal outcomes also cover already-satisfied operations: an old Archive/Restore cannot repeat after an opposite transition. Ordinary field edits read lifecycle state under the target lock. An archived target leaves its edit confirmation pending rather than consuming it as failure, so a User can explicitly restore and retry within the original expiry. This preserves the approved overwrite policy without introducing record-version rejection or extending confirmation validity. Ordinary browsing excludes archived records; explicit relationships and current Project hosting details retain them with status labels.

Ticket 07 uses paid interpretation only to select a constrained Project read operation. Deterministic rendering preserves Unknown values, archival labels, current sources and page coverage without entrusting facts to model generation. Inventory text never enters the interpreter. This limits prose flexibility but avoids another paid step and prevents inventory prompt injection from selecting operations. Private question checkpoints persist the plan, reservation identity, candidates and first selected Project; result controls reread live records. Stable context is separate, User/DM-bound and expires after 30 minutes. A started attempt cannot dispatch again after uncertainty, following the existing conservative shared spending policy.

Ticket 08 extends those checkpoints with validated inventory query plans whose exact references resolve to stable identifiers. Relationship reads follow the unique simple path between record kinds, preventing a shared catalog from creating inferred relationships between otherwise unrelated Projects. Correlated existence predicates count each target identity once. Current-record pages and totals share one SQL statement snapshot; a workspace inventory fingerprint restarts coverage after changes. This trades retained snapshot paging and uninterrupted progress during edits for current-record grounding and explicit coverage, without keeping duplicate inventory snapshots or paying to reinterpret later pages. Company-wide Tool status remains independent of explicit Project links.

Ticket 09 extends the constrained interpretation envelope with one mutation plan, then resolves it into a saved structured command. Re-entering the existing proposal handlers keeps field validation, actor/DM approval, overwrite, lifecycle, history and effect coordination in one mutation implementation. It trades conversationally inferred/implicit references for exact selectors and copied replacement text, clarifying ambiguous or missing data rather than guessing. A persisted resolved command freezes identities across restarts before proposal delivery, and a source column on existing confirmations distinguishes interpretation-backed changes in atomic history. No inventory text enters the model. Result navigation opens separate Cards keyed by the saved confirmation, so reading details/history cannot replace or refresh authorization or repeat spending.

Ticket 10 keeps the one-time operator import inside Documentation, separate from ordinary Slack single-record confirmations. An offline JSON cell snapshot avoids source credentials, formula evaluation and implicit synchronization; preparing a complete snapshot from an independently obtained export remains an operator responsibility. The exact source digest and resolved review identify the batch, with explicit User approval attribution. Records use stable workspace/source/kind/key identities. A workspace batch row serializes dedicated-connection transactions, each committing a record, its initial history and its effect checkpoint atomically. This permits partial progress and restart recovery without wrapping the whole inventory in one long transaction or replaying completed effects. Existing identities can only be referenced with reviewed matching fields; imports never overwrite them. Once effects exist the mapping is immutable; before any effect a new approved review can supersede a rejected batch with prior evidence retained. Reconciliation locks targets against concurrent Slack edits and verifies fields, relationships and initial history before recording authority. Successful replays only report current drift. Lifetime batch/effect provenance stays outside ephemeral cleanup. The [operator procedure](../documentation-import.md) defines transition and recovery; production source review/import remains separately authorized.
